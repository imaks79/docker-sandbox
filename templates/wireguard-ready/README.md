# wireguard-ready — туннель между хостом и контейнером

Готовый к работе WireGuard-сервер: собрали образ — при старте
контейнера автоматически создаются ключи, поднимается интерфейс `wg0`
и генерируется клиентский конфиг. Цель — потренироваться поднимать
VPN-туннель между вашим хостом (macOS/Linux/Windows) и контейнером.

## Быстрый старт

```bash
./sandbox.sh -n -p 51820:51820/udp -t wireguard-ready vpn
```

- `-n` — обязателен: даёт контейнеру capability `NET_ADMIN`/`NET_RAW` и
  доступ к `/dev/net/tun`, без этого WireGuard не сможет создать сетевой
  интерфейс.
- `-p 51820:51820/udp` — пробросить UDP-порт WireGuard наружу.

При старте в выводе `./sandbox.sh logs vpn` (или прямо в терминале при
первом запуске) увидите строку "WireGuard поднят..." и, если установлен
`qrencode` — QR-код конфига для мобильного приложения.

## Подключение с хоста

Клиентский конфиг лежит прямо на хосте, в `./workspace/wireguard/client.conf`
(генерируется автоматически, ничего вручную собирать не нужно).

1. Поставьте WireGuard-клиент:
   - macOS: `brew install wireguard-tools`, либо приложение WireGuard
     из App Store.
   - Linux: `apt install wireguard` / `pacman -S wireguard-tools`.
   - Windows: официальный клиент с wireguard.com.
2. Импортируйте `./workspace/wireguard/client.conf`.
3. Включите туннель и проверьте:

```bash
ping 10.66.0.1
```

Если пингуется — туннель между хостом и контейнером работает.

## Переменные окружения

| Переменная | По умолчанию | Что это |
|---|---|---|
| `WG_IFACE` | `wg0` | имя интерфейса внутри контейнера |
| `WG_PORT` | `51820` | UDP-порт WireGuard |
| `WG_SERVER_ADDR` | `10.66.0.1` | адрес сервера внутри туннеля |
| `WG_CLIENT_ADDR` | `10.66.0.2` | адрес клиента внутри туннеля |
| `WG_ENDPOINT_HOST` | `127.0.0.1` | адрес, который попадёт в клиентский конфиг как `Endpoint` |

Если подключаетесь не с той же машины, где крутится Docker (например,
с телефона в той же локальной сети), пересоберите образ с другим
`WG_ENDPOINT_HOST` (IP хоста в локальной сети):

```bash
# поправьте ENV WG_ENDPOINT_HOST в Dockerfile, затем:
./sandbox.sh -n -t wireguard-ready rebuild vpn
./sandbox.sh rm vpn
./sandbox.sh -n -p 51820:51820/udp -t wireguard-ready vpn
```

## Как это устроено

- `entrypoint.sh` при первом старте генерирует пару ключей сервера и
  клиента (`wg genkey`/`wg pubkey`) и сохраняет их в
  `./workspace/wireguard/` на хосте — они переживают `docker stop`/
  `docker start`, но не `docker rm` (тогда сгенерируются заново).
  ключи и клиентский конфиг тоже видны прямо на хосте.
- Дальше поднимается интерфейс `wg0` с одним peer'ом (клиентом) —
  это простой туннель "точка-точка" между хостом и контейнером, без
  маршрутизации через контейнер в интернет.
- Всё идемпотентно: повторные `docker start` не пересоздают интерфейс,
  если он уже поднят.

## Диагностика

- **"Operation not permitted" / интерфейс не создаётся** — забыли `-n`
  при создании контейнера. Опции применяются только при создании, нужно
  `./sandbox.sh rm vpn` и создать заново с `-n`.
- **Интерфейс не создаётся даже с `-n`, в логах "Не удалось создать
  интерфейс WireGuard"** — ядро Docker-хоста/VM собрано без поддержки
  WireGuard. Это не чинится внутри контейнера; контейнер всё равно
  останется живым (можно зайти и разобраться), но сам туннель работать
  не будет на этой машине.
- **Пинг не проходит, но интерфейс поднят** — проверьте, что порт
  51820/udp действительно проброшен (`-p 51820:51820/udp` при
  создании), и что в клиентском конфиге `Endpoint` указывает на
  реально достижимый адрес (см. `WG_ENDPOINT_HOST` выше).
- Посмотреть состояние внутри контейнера: `docker exec -it vpn wg show`.
