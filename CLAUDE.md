# CLAUDE.md

Инструкции для Claude Code при работе в этом репозитории.

## Что это за проект

`docker-sandbox` — учебная лаборатория для практики с Docker и Linux:
быстро поднимать контейнеры, экспериментировать, ломать и пересобирать,
не боясь испортить рабочую машину. Точка входа — `./sandbox.sh`
(см. `README.md`); готовые/учебные сценарии живут в `templates/`
(см. `LEARNING_IDEAS.md` для списка тем, которые здесь стоит развивать).

**Это не production-репозиторий.** Не предлагай практики "для прода"
(CI/CD gate, секрет-менеджеры с реальными ключами, публичные домены и
т.п.) — только то, что имеет смысл в локальной обучающей песочнице.

## Область работы

Этот проект — только про Docker-контейнеры (образы, Dockerfile,
`sandbox.sh`, шаблоны в `templates/`). Не превращай его в место для
несвязанных задач (не-докер скриптов, произвольного кода приложений и
т.п.) — если просят что-то в стороне от контейнеров, лучше уточнить,
не имелся ли в виду один из соседних проектов (`../dotfiles`,
`../fastinstall`, которые монтируются в `/workspace` через
`sandbox.sh`).

## Главное правило: каждый запрос — это шаблон

Когда пользователь просит "сделай контейнер для X" (любой сервис,
эксперимент, обучающий сценарий) — результатом должен быть **шаблон в
`templates/<имя>/`**, разворачиваемый одной командой через
`./sandbox.sh -t <имя> [опции] [имя-контейнера]`, а не разовый
одноразовый `docker run` в чате или файл вне этой структуры.

### Структура шаблона

```
templates/<имя>/
  Dockerfile          # обязателен — первая строка файла = краткое
                       # описание для `./sandbox.sh templates`
  entrypoint.sh        # если нужен демон/сервис в фоне (см. ниже)
  README.md или TUTORIAL.md   # инструкция по использованию
```

Два вида шаблонов, оба валидны — выбирай по смыслу задачи:

- **ready** (по образцу `templates/samba-ready`) — образ сразу
  собирает рабочий сервис. `README.md` с быстрым стартом на 2-3
  команды. Подходит, когда цель — "просто быстро поднять X".
- **manual** (по образцу `templates/samba-manual`) — минимальный
  образ (голая ОС + необходимые для тренировки утилиты, без самого
  сервиса) + `TUTORIAL.md` с пошаговыми командами для ручной настройки
  внутри контейнера. Подходит, когда цель — потренироваться настраивать
  сервис руками.

Если пользователь не уточнил — предпочитай **ready**, а **manual**
предлагай отдельно как вариант для тренировки (как уже сделано с
Samba).

### Технические детали, которые нужно учитывать

- `sandbox.sh` всегда запускает контейнер командой
  `docker run ... IMAGE sleep infinity` и остаётся живым за счёт этого
  `sleep infinity`, а не `CMD` образа. Поэтому любой демон (веб-сервер,
  БД, smbd и т.п.) должен подниматься через `ENTRYPOINT`-скрипт,
  который запускает сервис в фоне и затем делает `exec "$@"` — иначе
  сервис просто не запустится. См. `templates/samba-ready/entrypoint.sh`
  и `templates/samba-ready/Dockerfile` как рабочий пример (то же самое
  в `rsync-daemon`, `wireguard-ready`, `syncthing`). Исключение —
  `templates/systemd-timer`: там нужен настоящий init как PID 1, поэтому
  `entrypoint.sh` НЕ делает `exec "$@"`, а безусловно исполняет
  `exec /sbin/init`, игнорируя переданные аргументы — используй этот
  же приём, если шаблону принципиально важно, чтобы именно его процесс
  был PID 1, а не фоновым демоном.
- `/workspace` внутри контейнера — это `./workspace` на хосте
  (bind mount, настраивается в `sandbox.sh`, не в шаблонах). Если
  шаблону нужно "раздавать"/использовать файлы с хоста — используй
  `/workspace`, а не отдельный путь внутри образа, если пользователь
  явно не просил иначе.
- Сборка образа шаблона кэшируется по тегу `sandbox-template-<имя>:<имя
  контейнера>`; после правок `Dockerfile`/`entrypoint.sh` нужно
  `./sandbox.sh -t <имя> rebuild <имя-контейнера>`, иначе будет
  использован старый образ.
- Если сервису нужны сетевые порты наружу — не добавляй их в
  `sandbox.sh` намертво под конкретный шаблон (как уже сделано для
  Samba через `-s`); только для действительно частых/общих случаев.
  Для новых шаблонов по умолчанию используй универсальный `-p
  HOST:CONTAINER`, который уже есть в `sandbox.sh`, и опиши нужные порты
  в `README.md`/`TUTORIAL.md` шаблона.
- Если шаблону нужны повышенные привилегии (capability, `--privileged`,
  bind mount системных путей) — заведи для этого отдельный именованный
  флаг в `sandbox.sh`, а не молчаливый `--privileged` внутри шаблона:
  так пользователь явно видит и осознанно включает повышение прав.
  Уже есть прецеденты: `-n` (`--cap-add=NET_ADMIN,NET_RAW` +
  `/dev/net/tun`, для `firewall-lab`/`wireguard-ready`) и `-i`
  (`--privileged` + cgroup mount, для `systemd-timer`). Переиспользуй
  их для новых шаблонов с похожими требованиями вместо того, чтобы
  плодить дубликаты; для принципиально новых требований — заводи новый
  флаг по той же схеме и обязательно опиши в `usage()`/README, **что**
  именно он даёт контейнеру и почему это нужно — особенно если это
  `--privileged` или отключение security-опций, это заметное снижение
  изоляции, а не рутинная настройка.
- Не трогай персональные mount'ы `dotfiles`/`fastinstall` в
  `sandbox.sh` — это отдельные соседние проекты, не относящиеся к
  шаблонам.
- Тексты в репозитории (README, комментарии, сообщения скрипта) —
  на русском, как и весь остальной проект; пиши новые файлы в том же
  стиле.
- После значимых правок `sandbox.sh` — проверяй `bash -n sandbox.sh` и,
  если возможно, реальный прогон (`docker info` может быть недоступен —
  в этом случае явно скажи пользователю, что живой тест не проводился).
- Обновляй `./sandbox.sh templates` и корневой `README.md`, если
  добавляешь/переименовываешь шаблон — список шаблонов не должен
  расходиться с содержимым `templates/`.
